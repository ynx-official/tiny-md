## 范围与测量方式

按用户要求分析现有渲染开销与优化顺序。本轮没有实施生产代码优化，也没有更新已安装程序。
样本为用户指定的 `1. 0-1立项工具产品定义与共创工作流-V2.0.md`：39,594 字节、593 行，
237 行表格源码，实际识别 24 个表格、679 个数据 / 表头单元格、1 个 Mermaid 图。

在 `target/performance-analysis/source/` 创建隔离源码副本与文档副本，加入分段计时，
使用与本机发行程序一致的 release / thin LTO / x64 MSVC 静态 C 运行库参数构建诊断程序。
通过原生窗口实际打开、滚动、切换只读 / 源码模式、输入单字符并撤销。
输入只发生在副本的未保存缓冲区；原文及磁盘副本在采样后 SHA-256 均为
`9A33531D21C77BE58AEB7AF397F9933BF4D6BE91EAFFE6D19F053075B43CB587`。
安装程序哈希仍为 `6E493D74C8321976D1B90FFD3DFED3D3BDFFFE73FC42C577118E01333C2C55DD`。

计时覆盖编辑器 `render` 开始至编辑器绘制末尾，包括其布局、预绘制和绘制指令生成。
这是主线程路径的墙钟时间，不是 GPU 完成时间、端到端按键延迟或 FPS。
窗口其余代码、系统调度、屏幕录取和诊断计时本身也可能影响结果。
日志写入发生在测量结束之后；没有测量内存分配数量、GPU 占用或真实中文输入法压测。

原始 JSONL、汇总 JSON、诊断源码与 EXE 在 `target/performance-analysis/`，属于可清理的诊断产物。
以下表格固定记录本次汇总取样；冷态各只测一次，暖态包含空闲闪烁与少量交互帧，不能当成持续滚动帧率。

## 实测结果

| 场景 | 样本数 | CPU 路径 P50 | P95 | 说明 |
|---|---:|---:|---:|---|
| 首次打开排版文档 | 1 | 84.597 ms | — | render 自身 73.457 ms |
| 排版模式暖态 | 363 | 9.615 ms | 14.069 ms | 最慢 33.051 ms |
| 源码模式首次进入 | 1 | 46.112 ms | — | 字体 / 样式和换行缓存发生变化 |
| 源码模式暖态 | 138 | 4.667 ms | 8.441 ms | render 自身 P50 1.412 ms |
| 从源码返回排版 | 1 | 77.250 ms | — | 重新构建排版，Mermaid 也重新进入加载状态 |
| 只读模式静置 6 秒 | — | — | — | 日志条数 159 → 159，没有新增编辑器 render |

排版暖态的 `render` 自身 P50 为 3.864 ms，其内全文结构准备约 0.494 ms、
行布局约 2.582 ms（含表格单元格约 1.095 ms）、界面元素构建约 0.720 ms。
这些项目有包含关系，不能全部相加。其余耗时进入 GPUI 的布局、预绘制和绘制路径。
列宽权重计算本身 P50 只有 0.029 ms，不能把列宽算法单独认定为最大瓶颈。

滚动到正文 / 图形 / 表格区时，视口内分别约 25 / 1 / 17 个源行；每次仍处理全部 593 行和
679 个单元格，合计 1,272 次 `shape_text` 调用。单字符输入的采样也保留这一数量，
一次编辑器 CPU 路径为 13.828 ms。GPUI 已有字体布局缓存，调用数不等于 1,272 次底层字体重新排版。
光标相关稳定刷新间隔中位数约 534 ms，与 500 ms 的显隐周期相符。

## 瓶颈与证据

1. **全文行布局及元素树重建，缺少视口裁剪。**
   `markdown_editor.rs:1646` 每次收集表格，`:1664` 收集代码块，`:1751` 开始遍历全部源行，
   `:2046` 为全部非零高度行创建元素。没有按滚动可见区限制行布局或元素创建。
   即便只看到一个 Mermaid 预览，也继续处理文档后面的表格。

2. **光标闪烁刷新了整个编辑器。**
   `markdown_editor.rs:478` 每 100 ms 检查显隐，`:482` 对编辑器实体调用 `cx.notify()`。
   100 ms 检查不等于每秒十次重排，实际显隐变化通常每 500 ms 通知一次。
   但该通知走上述完整 `render`，光标在视口外时也一样。只读静置对照没有新增 render，
   支持光标通知是周期性全文刷新的直接触发点；最近加入的闪烁实现放大了既有重建开销。

3. **表格存在重复排版。**
   `markdown_editor.rs:1916` 先排版整行 Markdown 源码，随后表格数据行在 `:1984` 将 `row.text`
   清空，再在 `:2001` 为每个单元格独立排版。非编辑中的隐藏围栏也先排版再丢弃结果。
   整行表格源码的排版结果对实际网格显示没有用途；单元格计划、文字运行段和节点则在每帧重复构建。

4. **模式切换会清空缓存。**
   源码模式把 `blocks` 设为空，`syntax.rs:50`、`markdown_editor.rs:1676` 和 `:1687`
   随即删除高亮、图形视图和 Mermaid 结果。GPUI 0.2.2 的底层文字缓存以当前 / 上一帧为主，
   已退出呈现模式的字形布局不会长期保留。回到排版时再次出现 77 ms 冷态开销。

5. **同步与编辑派生数据是后续优化项。**
   `disk_sync.rs:23` 每秒唤醒并克隆文档基准，后台读完整文件；不变时没有触发额外渲染。
   每次文本变化还会重建全文字符串、统计字符、大纲和简介。它们有线性开销，但本次没有独立量化，
   不能与已测的全文绘制成本同等排序。Mermaid 已在后台生成且具有结果缓存；它不是每次闪烁重新解析。

## 建议实施顺序与验收

| 顺序 | 修改 | 验收重点 |
|---|---|---|
| 1 | 缓存文档结构、行 / 单元格布局，将光标显隐作为独立绘制状态；不可见光标不触发刷新 | 闪烁时没有 Markdown 解析或文本排版调用；保留正常颜色、显隐、选区和 IME 候选位置 |
| 2 | 表格数据行直接进入单元格布局；隐藏源码先判断可见性再排版；保留未改变模式的高亮 / Mermaid 缓存 | 同文档返回排版不重新生成图；表格分隔行编辑、源码模式和撤销仍正确 |
| 3 | 只创建可见行及前后缓冲区的元素，用高度索引和上下占位保持完整滚动范围 | 元素数随视口变化；滚动、选区拖动、大纲跳转、中文输入法和长图无跳位 |
| 4 | 以编辑版本和受影响块为单位更新布局，宽度 / 字体 / 主题变化明确失效；再按需要懒加载屏外布局 | 普通输入只更新当前块及受影响高度；整张表格列宽确实变化时才重新处理相关单元格 |
| 5 | 优化文件变更检测及快照共享，必要时合并字符统计 / 大纲刷新 | 保留原子替换文件的同步、同一处冲突保护和保存前原始字节核对 |

第一阶段可以保留全量高度元数据，仅虚拟化绘制元素，减少对现有光标映射的改动。
后续懒计算屏外高度时必须以当前可见行作为滚动锚点，防止高度修正导致正文跳动。
缓存键至少覆盖文本 / 块版本、宽度、字体、主题、呈现模式及当前语法揭示范围，
不能只按行号缓存而忽略输入法组词、选区或代码块状态。

性能目标建议按本机同文档复验：暖态 CPU 路径 P95 小于 8 ms，光标闪烁零文本重排，
源码往返复用未变化的图形结果。上述是待实施的验收建议，没有声称已达到或已修复卡顿。
